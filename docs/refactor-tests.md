# ドメイン層のテストのリファクタリング

CLAUDE.md の「コードレビューの観点」（特に「テスト名で振る舞いが読み取れるか。フィクスチャは `TestFixtures` に集約され、各テストは Arrange / Act / Assert が見分けられる構造になっているか」）と「テスト」の規約に沿って、ドメイン層のテストを見直した結果。

- 対象：`src/test/java/com/example/tsumory/domain/` の全 6 ファイル（2026-10-16 時点、コミット `41a0089`）
  - エンティティのテスト：`PostTest`・`DiaryTest`・`UserTest`・`PostCategoryTest`
  - マイグレーションとの突き合わせ：`PostContentCheckMigrationTest`
  - フィクスチャ：`TestFixtures`（ほかの層のテストからも使われている）
- 方法：テストと本体（`src/main/java/com/example/tsumory/domain/`）を読んで突き合わせた。コードは変えていない。テストのファイルにそのまま書かれた見えない文字は、バイト列を出して確かめた
- 前提：守っている振る舞い（何を拒否し、何を受け付けるか）は変えない。変えるのはテストの書き方と、足りないテストだけ。本体に手を入れる指摘（R9 の定数）はそう書いてある
- 重要度
  - **中**：今のままだと、テストが失敗したときに原因を追えない、またはテストが守りの抜けを見逃しうる
  - **低**：読みやすさ・一貫性の問題。テストの確かさには影響しない

### 指摘の状態の管理

`docs/code-review-*.md` と同じ運用にする。

- 状態は **未対応**・**対応済み**・**保留** の 3 つ。まとめの表の「状態」の列と、各指摘の「状態」の行の両方を直す
- 対応済みにしたら、各指摘の下に「✓ 対応済み」と解消メモ（日付、何をどう直したか、コミット）を書き足す。保留にしたら理由（誰がいつ、なぜそう判断したか）を書く
- 指摘を消さない
- 直すときは CLAUDE.md の「テスト」に従い、書き換えたテストが空振りしていないかを、本体の守りを一度外して確かめる（書き換えの前後で、同じ守りを外すと同じテストが落ちること）

## テストの確かさ

### R1. テストのソースに見えない文字がそのまま書かれている（中）

- 状態：対応済み
  - ✓ 対応済み（2026-10-16、コミット `3522def`）：`PostTest` の U+200B・U+202E・U+2028・U+FEFF（80〜82・85・107 行目）と、絵文字の U+200D・U+FE0F（98 行目）を `\u200B` などのエスケープに置き換えた。同じ配列の NEL・タブとそろった。絵文字は、確かめたいつなぎ文字・異体字セレクタだけをエスケープにし、絵文字本体は文字のまま残した。バイト列で見て、ファイルに見えない文字が残っていないことを確かめた。`Post` の見えない文字のチェックを一時的に外すと、`見えない文字を含む本文では作れない`・`見えない文字を含む本文には直せず元の本文のまま` の 2 つが落ちることも確かめた（書き換えで空振りしていない）
  - 直し方の 3 つ目（見えない文字を直接書かないことの確かめを、テストのソースにも広げる）は入れていない。絵文字のつなぎ文字（U+200D）・異体字セレクタ（U+FE0F）を文字のまま書くことを許すかが決まっていないため。今の `PostTest` はどちらもエスケープで書いたので、広げるなら全部の文字を対象にできる
  - 作業メモ：Claude Code の Edit ツールに `\u200B` と書くと JSON のエスケープとして読まれ、見えない文字そのものが書き込まれる（ツールの表示でも `\u` が消えて見える）。エスケープを書くときは、バイト単位の置換（`\x5C` でバックスラッシュを書く）で入れ、`od` などでバイト列を確かめる。このファイルも、最初のコミット（`30a19d0`）の時点で R1 の説明の 9 か所に見えない文字そのものが入っていたので、R1 の記録といっしょに直した
- 場所：`PostTest`
  - 80 行目 `"昼は\u200Bカレー"`：U+200B（ゼロ幅スペース）
  - 81 行目 `"昼は\u202Eーレカ"`：U+202E（右から左への上書き）
  - 82 行目 `"昼は カレー"`：U+2028（行区切り）
  - 85 行目 `"昼は\uFEFFカレー"`：U+FEFF（BOM）
  - 107 行目 `post.edit("昼は\u200Bカレー", ...)`：U+200B
  - 98 行目の絵文字（U+200D・U+FE0F）も文字そのもの
  - 一方、83 行目の NEL は `\u0085`、84 行目のタブは `\t` とエスケープで書いていて、同じ配列の中で書き方が混ざっている
- 何が起きるか
  - 画面やレビュー（GitHub の差分など）では `"昼はカレー"` としか見えず、どの文字を確かめているかをコメントでしか読み取れない。コメントと中身がずれても気づけない（たとえば 82 行目を U+2029（段落区切り）に変えても、見た目は同じ）
  - 81 行目の U+202E は、エディタや差分の表示で後ろの文字の並びをひっくり返す（Trojan Source と同じ見え方）。ここではテストの値として意図して使っているが、ソースの読みやすさを損ねる
  - エディタやツールが見えない文字を取り除くと（BOM の除去など）、そのケースは普通の本文になる。拒否するはずのテストが落ちるので空振りにはならないが、原因がソースから読めない
  - CLAUDE.md は、マイグレーションについて「見えない文字をファイルに直接書かない」と決めていて、`PostContentCheckMigrationTest#マイグレーション自体に見えない文字を直接書かない` で確かめている。テスト自身が同じ決まりを守っていない
- 直し方
  - 見えない文字は `\u200B` のようにエスケープで書く（`"昼は\u200Bカレー"`）。補助面の文字（タグ文字）は今の `TestFixtures.hiddenAscii` のように、コードポイントから作る
  - 絵文字のつなぎ文字（98 行目）も `"👨\u200D..."` と書くと読めなくなるので、`"家族で公園" + "👨" + "\u200D" + "👩" + ...` のように、確かめたい U+200D だけをエスケープにする
  - 再発を止めたいなら、`PostContentCheckMigrationTest#マイグレーション自体に見えない文字を直接書かない` と同じ確かめを、`src/test/java/**/*.java` にも広げる（U+200D・U+FE0F の扱いを決める必要がある。決まらないなら広げない）

### R2. 拒否するケースを配列の `for` で回している（中）

- 状態：対応済み
  - ✓ 対応済み（2026-10-16、コミット `f43fff9`）：場所に挙げた 7 つのテストを、`@ParameterizedTest` + `@MethodSource` + `Arguments.argumentSet`（名前付きの引数）に置き換えた。空白や見えない文字は `@ValueSource` だとテストの結果で見分けられないので、全部名前を付けた（例：`[2] ゼロ幅スペース U+200B`、`[3] 全角スペースだけ`）。見えない文字の名前は、もとの行末のコメントをそのまま使い、コードポイントを足した。`UserTest#ユーザー名は空でなく上限の文字数まで` は、`上限の文字数までのユーザー名で作れる` と `空や上限を超えるユーザー名では作れない` に分けた。確かめる中身（例外の型・メッセージ）は変えていない（R3・R5 で扱う）

- 場所
  - `PostTest`：`改行を含む本文では作れない`（22 行目）・`空や空白だけの本文では作れない`（57 行目）・`見えない文字を含む本文では作れない`（78〜91 行目）・`絵文字のつなぎ文字や全角スペースは使える`（98 行目）

  - 見えない文字は、名前付きの引数（`@MethodSource` で `Arguments.argumentSet("ゼロ幅スペース U+200B", "昼は\u200Bカレー")`）にすると、テストの結果に文字の名前が出る。今の行末のコメントが、そのまま名前になる
  - 単純な値は `@ValueSource(strings = {...})`。空文字列・空白は `@ValueSource` に書くか、`@EmptySource` を使う
  - `UserTest#ユーザー名は空でなく上限の文字数まで` のように、受け付ける側と拒否する側が 1 つのテストに入っているものは、2 つのテストに分ける

### R3. 「失敗したら前の状態のまま」の確かめ方がそろっていない（中）

- 状態：対応済み
  - ✓ 対応済み（2026-10-16、コミット `88c8f82`）：`PostTest`・`DiaryTest` に `assertUnchanged` を置き、失敗した操作のテストはすべてこれで確かめるようにした。`Post` は本文・投稿時刻・更新時刻・「編集済み」・カテゴリ・手で直した印、`Diary` は本文・生成時刻・日付を `assertSoftly` でまとめて見る。`Post#edit` の失敗（空白・上限超え・改行・見えない文字）は、1 つのパラメータ化テスト `決まりを破る本文には直せず元の本文のまま` にまとめ、1 ケースごとに確かめる。`カテゴリにnullは入れられない` もこのヘルパーで見る
  - 空振りの確認：`Post#edit` の先頭で更新時刻を先に書き換えると、`決まりを破る…` の 4 ケースと `時刻がnullなら直せず元の本文のまま` が落ちた（前は見えない文字のケースが更新時刻を見ていなかったので、このケースでは気づけなかった）。`Diary#updateContent` の先頭で本文を先に書き換えると、書き直しの失敗のテストが 3 つとも落ちた
- 場所と、確かめている値

  | テスト | 本文 | 更新時刻・生成時刻 | カテゴリ |
  |---|---|---|---|
  | `PostTest#時刻がnullなら直せず元の本文のまま` | ○ | ○ | － |
  | `PostTest#見えない文字を含む本文には直せず元の本文のまま` | ○ | **×** | － |
  | `PostTest#空や上限を超える本文には直せず元の本文のまま` | ○（2 ケースのあとに 1 回だけ） | ○（同上） | － |
  | `PostTest#改行を含む本文には直せず元の本文のまま` | ○ | ○ | － |
  | `PostTest#カテゴリにnullは入れられない` | － | － | ○ |

- 何が起きるか
  - CLAUDE.md の「状態を変えるメソッドは、すべての値を確かめてから書き換える」を守っているかは、このテストだけが見張っている。今の `Post#edit` は時刻 → 本文の順に確かめてから書き換えているので問題ないが、たとえば「本文を書き換えてから時刻を確かめる」順に崩れたとき、`見えない文字を含む…` のテストは更新時刻を見ていないので、どのテストで気づけるかが偶然に頼る
  - `空や上限を超える…` は 2 つの失敗のあとにまとめて 1 回だけ確かめているので、1 つ目の失敗で書き換わっていても、2 つ目の失敗が元に戻すことはないので気づける。ただし、どちらのケースで壊れたかは分からない
  - 同じ 2〜3 行の確かめを、テストごとに書いている
- 直し方
  - 「前の状態のまま」をヘルパーにする。たとえば `PostTest` に `assertUnchanged(Post post)`（本文 `LUNCH`・更新時刻 `POSTED_AT`・カテゴリ `OTHER`・手で直した印なし・`isEdited()` が false）を置き、失敗のテストはすべてこれで確かめる。`DiaryTest` にも同じものを置く
  - R2 と合わせて、失敗の値を `@ParameterizedTest` で渡し、1 ケースごとに `assertUnchanged` する

  - **本文の文字数を `String#length()` で数えること**：`Post` の Javadoc に「文字数はフォームの `@Size` と同じく `String#length()` で数える」と書いてあるが、テストがない。絵文字（サロゲートペア）50 個はちょうど 100 で作れ、51 個は作れないことを確かめると、この決まりが明示される（フォームと数え方がずれたら気づける）

### R10. `DiaryTest` の境目のテストが 3 つのことを確かめている（低）

### R11. `PostContentCheckMigrationTest` の名前と中身がずれている（低）
