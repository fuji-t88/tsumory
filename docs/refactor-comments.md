# コメントとドキュメントの置き場所の見直し

「なぜこの設計にしたのか」は仕様書に書き、コードのコメントには書かない、という方針（書籍の原稿「仕様書が設計意図の正本になる」「テストコードが『実行可能なドキュメント』になる」「それでも JavaDoc が有効な場面はある」）に合わせて、CLAUDE.md とコードのコメントを見直した記録。

- 対象：`src/main/java/` のコメントすべて（2026-10-16、見直す前はコミット `9cdb5ec`）
- 方法：コメントを全部書き出し、仕様書（`docs/phase1-spec.md`・`docs/phase2-spec.md` など）と CLAUDE.md に同じ理由が書かれているかを突き合わせた
- 決めた方針：CLAUDE.md の「コーディング規約 > コメントとドキュメントの置き場所」と「テスト」（このファイルと同じコミットで足した）

## 数字で見る効果

前（`9cdb5ec`）と後（`43df72e`）を、同じ方法で測った。

| 測るもの | 前 | 後 | 測り方 |
|---|---|---|---|
| コメントの行数（`src/main/java`） | 517 | 492 | 行の頭が `//`・`/**`・`*`・`/*` の行 |
| うち `domain/` | 90 | 67 | 同上 |
| 仕様書・CLAUDE.md の節への参照（`xxx.md の「…」`） | 12 | 36 | 折り返しをつないで「…」を数えた（`DocReferenceTest` と同じ拾い方） |
| どのファイルか分からない参照（「仕様 6 章」「仕様書の 8 章」） | 2 | 0 | `git grep` |
| 実装や仕様と食い違っていたコメント（見つけたもの） | 2 | 0 | 下の「乖離していたコメント」 |
| 業務ルールを含むのに JavaDoc がない、service の公開メソッド | 1（`PostService#delete`） | 0 | 公開メソッドを書き出して確かめた。`today()`・`countPosts()` は名前で分かるので数えない |
| 参照が実在する節を指すかを確かめる仕組み | なし | `DocReferenceTest`（本体 36・テスト 7 の参照） | |
| 英語のテスト名 | 117 | 117 | 変えていない（「判断の前提と見直す条件」） |

- 本体のコードは、コメントの行だけが変わった（コメントでない行の差分が 0 行であることを確かめた）
- `docs/` と CLAUDE.md を Gradle のテストの入力に足した（`build.gradle.kts`）。足す前は、文書だけを直したときにテストが「最新」として飛ばされ、`DocReferenceTest`・`SourceInvisibleCharsTest` が流れなかった（このファイルを書いたあとに `./gradlew test` が 4 秒で終わったことで気づいた）。足したあと、`docs/spec.md` だけを変えて `test` が流れることを確かめた
- `DocReferenceTest` が空振りしていないことは、参照を一時的に壊して確かめた。1 行の参照（`Post` の `「4. ドメインモデル」` を `「4. ドメインの設計」` に）と、Javadoc の途中で折り返した参照（`「5. 画面 > 入力チェック…」` を `「5. 画面 > 入口チェック…」` に）の両方で落ちた

## 乖離していたコメント

原稿が言う「コード内コメントは更新が忘れられがちで、実装と乖離する」が、実際に 2 つ起きていた。

| 場所 | コメント | 何がずれていたか | 直し方 |
|---|---|---|---|
| `DiaryGenerationService#generateForDate` | 「findPostsByDate / saveDiary はそれぞれ独立したトランザクションを張る」 | 指摘 11（code-review-service.md）で `availableRange` の読み取りが足されたが、コメントは 2 つのままだった。中身も CLAUDE.md の「Spring・Lombok」の繰り返し | 3 つを並べ、理由は CLAUDE.md の節への参照にした |
| `DiaryController#generateDiaryForDate` | 「原稿にはないが、Claude API の失敗で 500 にならないよう…」 | 今の phase2-spec.md の「6. 処理の詳細 > 日記生成・再生成」には、この扱いがはっきり書いてある。仕様書が追いついたあとも、コメントが残っていた | 仕様書の節への参照にした |

## 直したコメント

| 種類 | 場所 | 直し方 |
|---|---|---|
| 仕様書の理由の繰り返し | `Post`（見えない文字の定義・カテゴリの初期値・手で直した印・`assignCategory`・本文の決まり・改行の禁止）、`Diary`（本文の決まり・生成時刻の境目）、`User`（BCrypt のハッシュの形）、`PostCategory`、`PostForm`、`ClaudeService#buildUserMessage`、`PostCategoryClassifier`（分類のタイムアウト）、`ClaudeProperties`、`AnthropicConfig` | 何をするか（契約）は残し、理由は仕様書の節への参照にした |
| CLAUDE.md の繰り返し | `PostService#create`・`#edit`（トランザクションを分ける理由）、`InputLimitsAdvice`、`AnthropicConfig`（API キーの読み方） | CLAUDE.md の節への参照にした |
| どのファイルか分からない参照 | `AnthropicConfig`（仕様 6 章）、`NotFoundExceptionHandler`（仕様書の 8 章） | ファイルと節の名前で書いた |
| コードを読めば分かること | `DiaryController`（`@RequestMapping` があるので相対で書く）、`User`（2 つの行コメント。理由は仕様書と CLAUDE.md にある） | 消した |
| JavaDoc がない | `PostService#delete` | 足した（今日と昨日の自分のつぶやきだけ消せる。他人のものと存在しないものを区別しない） |

残したもの（その行を読む人が、その場で要る事情）の例：`Diary#updateContent` の「先に両方を確かめる」、`PostService#create` の「判定を待つ間に、別のタブなどから投稿されていないか確かめ直す」、`RequestLoggingFilter` の行コメント（下の表）、`PostRepository` の半開区間の理由、`LikeKeyword` の置き換えの順番、`DiaryService#findDiaryForSummary` の「ここで今日を求め直すと…」。

仕様書にない設計の意図を、コメントから仕様書へ移したものはない。直したコメントの理由は、どれも仕様書か CLAUDE.md にすでに書かれていた。ただし、残したコメントのすべてを仕様書と 1 つずつ突き合わせたわけではない。

## よくできている点

- **仕様書が、決まりの理由まで書いている**（phase1-spec.md の「3. ドメインモデル」、phase2-spec.md の「5. 画面 > 入力チェック（変更。投稿・編集共通）」など）：コメントを参照に変えても、理由が失われなかった。原稿の「仕様書が設計意図の正本」をもとから満たしていた
- **一部のコメントは、もとから仕様書を参照していた**（`DiaryDateRange`・`PostCategoryClassifier`・`PostCategory`）：今回の書き方の手本にした
- **業務ルールを含む公開メソッドの JavaDoc が、例外と条件を並べている**（`DiaryGenerationService#generateForDate` の、どの日付で何を投げるかの一覧）：原稿の「複雑なビジネスルールを含むメソッドには JavaDoc が有効」をもとから満たしていた
- **テスト名が振る舞いを表している**：日本語（`決まりを破る本文には直せず元の本文のまま`）も英語（`create_rejectsWhenDailyLimitReached_withoutCallingClaude`）も、原稿の `delete deletesOwnPost` と同じく、そのまま仕様として読める

## 判断の前提と見直す条件

| 判断 | 前提 | 見直す条件 | 状態 |
|---|---|---|---|
| 英語のテスト名（service・repository の 117 件）は今は直さず、そのテストクラスを直すときに日本語にする | 一度に直すと差分が大きく、ほかの変更とまざってレビューしにくい。英語の名前も振る舞いは読める | service のテストを大きく直すとき、または日本語と英語のまざりで読みにくいと感じたとき | 今のまま |
| `RequestLoggingFilter` の行コメントは、CLAUDE.md の「リクエストの追跡」と重なるが残す | どれも、その行の順番や書き方の理由（MDC が残っているうちにログを出す、`MDC.clear()` を使わない）で、CLAUDE.md を読まずに直すと壊れる | CLAUDE.md の「リクエストの追跡」の中身が変わったとき（コメントと食い違っていないか確かめる） | 今のまま |
| `DocReferenceTest` は `src/` の `.java` だけを見る | テンプレート・SQL・設定ファイルには、節への参照を書いていない | テンプレートや SQL に参照を書くようになったとき | 今のまま |
| 見出しは前方一致で比べる（「3. ドメインモデル」は「3. ドメインモデル（`domain/`）」に当たる） | 仕様書の見出しには、括弧書きやエンドポイントが付くことが多い | 前方一致で、別の節に取り違えて当たることが起きたとき | 今のまま |
| `DocReferenceTest` を `domain` パッケージに置く | ソース全体を見るテストは `SourceInvisibleCharsTest` と同じ場所にそろえる。パッケージは 6 つだけの決まり（CLAUDE.md の「パッケージの分け方」）で、置き場がほかにない | ソース全体を見るテストが増えたとき | 今のまま |
| 「コードのコメントには設計の意図を書かない」は、テストのコメントには当てはめない | テストのコメントは、そのテストが何を守っているかの説明で、テスト名と合わせて「実行可能なドキュメント」の一部になっている（docs/refactor-tests.md の「よくできている点」） | テストのコメントと仕様書が食い違っているのが見つかったとき | 今のまま |
