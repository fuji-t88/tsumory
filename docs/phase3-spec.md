# フェーズ 3 詳細仕様（写真・音声）

つぶやきに写真を 1 枚まで添付できるようにし、本文を音声認識でも入力できるようにする。
フェーズ 1・2 の仕様（[phase1-spec.md](phase1-spec.md)・[phase2-spec.md](phase2-spec.md)）を土台にし、この仕様書には**追加・変更する部分だけ**を書く。食い違う場合は、この仕様書を正とする。
パッケージ構成・コーディング規約・禁止事項は [CLAUDE.md](../CLAUDE.md) に従う。仕様書の一覧は [spec.md](spec.md)。

要件・受入条件・テストケース・マイルストーンは、リポジトリ直下の WBS（`WBS_tsumory.md`。Excel は `WBS_tsumory.xlsx`）で管理する。この仕様書は、WBS の要件を実装に入れる粒度まで詳しくしたもので、要件 ID（`PH-REQ-01` など）で WBS と対応させる。WBS と食い違う場合は、この仕様書を正とし、WBS を直す。

## 2. 写真の保存先（PostgreSQL）

写真は、アプリの DB（PostgreSQL）の `post_photos` テーブルに、バイナリ（`BYTEA`）で保存する。

- WBS の D-04 では、Railway の非公開のオブジェクトストレージ（S3 互換のバケット）を第一候補にしていた。2026-11-20 に Railway の試用期間が終わり、無料のまま続けると決めたので、外部のストレージを使わない形に変えた
- DB に入れる理由
  - 追加のサービス・料金・資格情報が要らない
  - つぶやきと写真を同じトランザクションで保存・削除できる。DB とストレージの食い違い（片方だけ残る、孤立したファイル）が起きないので、WBS の D-07（補償処理と清掃）が要らなくなる
  - つぶやきを消すと、写真も外部キーの `ON DELETE CASCADE` で一緒に消える（PH-REQ-13 の「投稿の削除で画像が使えなくなる」を DB が守る）
- 引き受けること：DB が写真の分だけ大きくなる（1 枚 5MB まで × 1 日 16 件まで）。バックアップと復元に時間がかかるようになる
- 見直す条件：DB の大きさが無料の枠や性能の限界に近づいたとき、複数の写真や大きな画像を扱うことになったとき。そのときは外部のストレージに移し、D-07 の補償処理を設計する
- 写真は `posts` とは別のテーブルにする。つぶやきの一覧・検索・日記の生成で `posts` を読むときに、写真のバイナリを読まないため

## 3. データベース

### マイグレーション

`V4__create_post_photos.sql` で `post_photos` を作る。

### `post_photos`

| 列 | 型 | 制約 | 説明 |
|---|---|---|---|
| `post_id` | `BIGINT` | 主キー、`posts(id)` への外部キー（`ON DELETE CASCADE`） | 写真を添付したつぶやき。主キーなので、1 つのつぶやきに写真は 1 枚まで |
| `content_type` | `VARCHAR(100)` | `NOT NULL` | 写真の形式（`image/jpeg` など）。許す形式は PH-REQ-02 で決める |
| `size_bytes` | `INTEGER` | `NOT NULL`、`data` の長さと同じ | 写真の大きさ（バイト） |
| `data` | `BYTEA` | `NOT NULL`、空でない | 写真のバイナリ |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL` | 写真を保存した日時 |

- 「1 つのつぶやきに 1 枚まで」は、主キー（`post_id`）で DB が守る
- 検査制約で守るもの：`data` が空でない、`size_bytes` が `data` の長さと同じ（内部一貫性。CLAUDE.md の「入力の検証（多層防御）」）
- 容量の上限（5MB。PH-REQ-03）と形式（PH-REQ-02）は、仕様が変わりうる業務ルールなので、DB の検査制約には入れない
- 差し替え（PH-REQ-05）のための `updated_at` は、差し替えを実装するときに足す

## 4. ドメインモデル（`domain/`）

`PostPhoto`（エンティティ。`post_photos`）を足す。

- `Post` との関係は `PostPhoto` の側だけが持つ（`@OneToOne(fetch = LAZY)` + `@MapsId`）。`Post` には写真への参照を持たせない（つぶやきを読むたびに写真を読まないため）
- コンストラクタ `PostPhoto(Post post, String contentType, byte[] data, Instant now)` で、内部一貫性を確かめる
  - 値が `null` なら `NullPointerException`
  - `contentType` が空・空白だけ・100 文字を超えるとき、`data` が空のときは `IllegalArgumentException`
- `data` は受け取るときと返すときに複製する（外から書き換えられないように）

## 5. 画面

### 今日のつぶやき（変更。`templates/home.html`、`/`）

投稿フォームに、写真を選ぶ欄を足す。

```
┌ いまの気持ちをつぶやく ────────────────┐
│ ┌──────────────────────────┐ │
│ │（本文）                              │ │
│ └──────────────────────────┘ │
│ 写真（任意・1 枚まで） [ファイルを選択]    │
│                              [つぶやく] │
└──────────────────────────────┘
```

- フォームは `enctype="multipart/form-data"` で送る
- ファイルの欄（`<input type="file" name="photo">`）は 1 つだけで、`multiple` を付けない
- 写真を選ばなくても投稿できる（任意）
- 入力チェックで画面を出し直すとき、選んだ写真は残らない（ブラウザの仕様）。本文は残る
- 投稿の上限に達しているときは、本文の欄と同じく写真の欄も無効にする
- 写真の欄の下に、受け付ける形式と大きさの案内（「JPEG か PNG・5MB まで」）を出す。`accept` は `image/jpeg,image/png`
- 写真を選んだらすぐに、その写真をフォームの中にプレビューする（PH-REQ-04）。横の「写真を外す」で選択を取り消せ、外したあとは写真の欄にフォーカスを戻す。プレビューはブラウザの中だけで作り（`URL.createObjectURL`）、送る前にサーバーへは送らない。Content-Security-Policy を入れるときは、`img-src` に `blob:` を許す
- 送る前に、ブラウザでも形式と大きさを確かめる（`static/js/photo-input.js`）。受け付けないファイルを選んだら、選ばなかったことにして、サーバーと同じメッセージを出す。数字とメッセージは、サーバーが `data` 属性で渡す（JavaScript に書かない）。JavaScript が無効でも、サーバーが同じ決まりで断る
- 添付した写真を一覧に表示するのは PH-REQ-11 で作る

### 入力チェック（追加）

| 対象 | 決まり | メッセージ |
|---|---|---|
| 写真 | 1 枚まで（`photo` の部分が 2 つ以上送られたら拒否。画面からは送れないが、リクエストを直接作れば送れる） | 写真は 1 枚まで添付できます |
| 写真 | 空でない | 写真のファイルが空です |
| 写真 | 5MB まで | 写真は 5MB 以内にしてください |
| 写真 | JPEG か PNG（中身で判定する） | 写真は JPEG か PNG にしてください |
| 写真 | 幅・高さ 12,000 画素まで、かつ 5,000 万画素まで | 写真の画素数が多すぎます（5000 万画素まで） |
| 写真 | 画像として読める | 写真を読み込めませんでした。別の写真を選んでください |

- ファイル名も中身も空の部分（写真を選ばなかったときにブラウザが送る部分）は、写真がないものとして扱う。ファイル名があれば、中身が空でも写真として扱い、「空です」で断る（空のファイルを選んだのに、黙って写真なしで投稿しない）
- 写真の決まりで断ったときは、本文を残して画面を出し直し、写真の欄にメッセージを出す（選んだ写真は残らない）
- 枚数はフォームの入力チェック（`PostForm`）、それ以外は service（`PhotoValidator`）で確かめる。上限・形式は仕様が変わりうる業務ルールなので、エンティティと DB には入れない（CLAUDE.md の「入力の検証（多層防御）」）

## 6. 処理の詳細

### つぶやきの投稿 `POST /posts`（変更）

1. フォームの入力チェック（本文と写真の枚数）
2. 写真があれば、controller が `MultipartFile` から、形式（ブラウザが送った `Content-Type`。なければ `application/octet-stream`）とバイナリを取り出して `PhotoUpload`（service の record）にし、`PostService#create` に渡す。service は Web の型（`MultipartFile`）を知らない
3. `PostService#create` は、これまでどおり上限の確認 → カテゴリの分類（Claude API。トランザクションの外）→ 保存の順に進める。写真は、つぶやきと**同じトランザクション**で保存する。どちらかが失敗したら、両方とも保存されない
4. ログ（INFO）に、写真の有無と大きさ（バイト）を足す。写真の中身・ファイル名は出さない（ファイル名に個人的な内容が入りうるため。CLAUDE.md の禁止事項「ログ」と同じ考え）

- 分かっている制約：開発の設定（`application.yaml` の `org.hibernate.orm.jdbc.bind: TRACE`）では、SQL のバインドパラメータのログに、写真のバイナリが 16 進でそのまま出る（2026-11-20 に 1.5MB の写真で確かめ、約 700 万文字の 1 行になった）。本番は `INFO` にしているので出ない（CLAUDE.md の「本番のコンテナ」）。開発で写真を何枚も試すときは、この設定を一時的に `INFO` にする

### 写真の検証

`service/PhotoValidator#inspect` が、次の順に確かめる。どれかで断ったら `InvalidPhotoException`（理由つき）を投げ、何も保存しない。`PostService` は、上限の確認と Claude API の呼び出しより前に確かめる（受け付けない写真に料金をかけない）。断ったときは、理由と大きさを WARN で記録する（中身は出さない）。

1. 空でない
2. 5MB（`MAX_BYTES`）以下。ちょうど 5MB は受け付ける
3. 形式：データの先頭のバイト（マジックナンバー）で JPEG（`FF D8 FF`）か PNG（`89 50 4E 47 0D 0A 1A 0A`）かを決める。ブラウザが送った `Content-Type` とファイル名は使わない（拡張子・MIME の偽装を通さない）。GIF・HEIC・WebP は受け付けない
4. 画素数：ImageIO でヘッダーだけを読み、幅・高さが 12,000 画素（`MAX_SIDE`）以下、幅 × 高さが 5,000 万画素（`MAX_PIXELS`）以下か。画像のデータを展開する前に確かめる（小さなファイルが巨大な画像に展開される、解凍爆弾への備え。WBS の D-03）
5. 中身：最後まで読み込めるか。100 万画素ほどになるよう間引いて読む（メモリを使いすぎないため）。途中で切れたデータは、ImageIO が例外ではなく警告を出すので、警告も壊れているとみなす

- 保存する形式（`post_photos.content_type`）は、3. で決めたもの（`image/jpeg` か `image/png`）
- 撮影位置などのメタデータ（EXIF・GPS）は取り除かない。写真を見られるのは投稿した本人だけなので（PH-REQ-08）、ほかの人に位置が漏れない。取り除くには画像を書き出し直す必要があり、画質と向きの情報（EXIF の回転）を失うため（WBS の D-08）。ほかの人に写真を見せる機能を作るときは見直す
- CMYK の JPEG など、ImageIO が読めない JPEG は「読み込めませんでした」になる

### アップロードの大きさ（設定）

- Spring の既定（1 ファイル 1MB）では、スマートフォンやカメラの写真の多くが送れない。`spring.servlet.multipart.max-file-size` を 10MB、`max-request-size` を 11MB（写真 + 本文などのフォームの値）にする
- 受け付ける上限（5MB）より大きくしているのは、上限を少し超えた写真にも「5MB 以内にしてください」を出すため（5MB を超えた写真は、`PhotoValidator` が断る）
- 10MB を超えるリクエストは、Spring と Tomcat が受け取らない。そのときは汎用のエラー画面になる（画面からは、ブラウザの確かめで 5MB を超える写真を送らせない）

## 7. セキュリティ

- CSRF：`multipart/form-data` のフォームも `th:action` で送り、CSRF のトークンを埋め込む（CLAUDE.md の禁止事項「CSRF」）
- 写真はログイン中のユーザーのつぶやきにだけ付く（新しく作るつぶやきに付けるので、他人のつぶやきを指定する経路はない）
- 写真の形式・中身は、サーバーがデータから確かめる（「6. 処理の詳細 > 写真の検証」）。ブラウザの確かめ（`photo-input.js`）は使い勝手のためで、守りはサーバーに置く

## 8. テスト

- `PostPhotoTest`：コンストラクタの内部一貫性（`null`・空の形式・長すぎる形式・空のデータを拒否する、データを複製する）
- `PostServiceTest`：写真ありの投稿で、つぶやきと写真を同じトランザクションの中で保存する。写真なしなら写真を保存しない。上限に達していたら写真も保存しない
- `PostControllerTest`：写真なし・写真 1 枚で投稿できる。写真 2 枚は入力チェックで拒否し、service を呼ばない。ファイル名も中身も空の部分は写真なし、ファイル名のある空のファイルは写真として渡す。受け付けない写真は理由を出し、本文を残す
- `PhotoValidatorTest`：JPEG・PNG を受け付け、GIF・HEIC・偽装した HTML やテキスト・空・5MB を超える・途中で切れた・画素数が上限を超えるものを断る。5MB ちょうど、画素数の上限ちょうどは大きさ・画素数では断らない。テストの画像は ImageIO で作り、大きすぎる画素数は PNG のヘッダーだけを組み立てて試す（`TestFixtures`）
- DB の制約（主キーで 2 枚目を拒否する、検査制約、つぶやきの削除で写真も消える）は、テストが DB につながないので、開発の DB でトランザクションの中で確かめ、最後にロールバックする（CLAUDE.md の「テスト」）
