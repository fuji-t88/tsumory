# 公開 URL の Basic 認証のレビュー

公開 URL の Basic 認証（`config/BasicAuthFilter`。phase1-spec.md の「7. セキュリティ > 公開 URL の Basic 認証」）を、依頼された 4 つの観点と CLAUDE.md の「コードレビューの観点」で見た結果。ほかのレビューは [code-review-service.md](code-review-service.md)・[code-review-non-service.md](code-review-non-service.md)・[code-review-static-analysis.md](code-review-static-analysis.md)。

- 対象（2026-10-19 時点、コミット `13e2b24`）：`BasicAuthFilter`・`BasicAuthFilterTest`。あわせて `SecurityConfig`・`RequestLoggingFilter`（順番と影響を見るため）
- 方法：コードを読んで観点と照らし合わせた。観点ごとに、テストと実際のコンテナ（環境変数あり・なし・片方だけの 3 通り）で確かめた。守りを 7 通りわざと壊して、テストが捕まえるかも確かめた
- 指摘の重要度と状態の付け方は [code-review-non-service.md](code-review-non-service.md) の「指摘の状態の管理」と同じ

## 依頼された観点

| 観点 | 結果 | 根拠 |
|---|---|---|
| 環境変数がないときは無効になるか | 満たす | `@Value("${BASIC_AUTH_USERNAME:}")` で、環境変数がなければ空になる。両方が空なら `shouldNotFilter` が `true` を返し、すべて素通しする。テスト「環境変数がなければ資格情報なしで通す」と、環境変数なしのコンテナで `/login` が 200 になることで確かめた |
| フォームログインより先に実行されるか | 満たす | `@Order(SecurityFilterProperties.DEFAULT_FILTER_ORDER - 1)` で Spring Security のフィルターの 1 つ前に置く（数字でなく基準からの相対）。テスト「Spring Security のフィルターより前に動く」があり、順番を後ろにずらすと落ちる。コンテナでも、資格情報なしの `/login` は 401 になった（ログイン画面は見えない） |
| 既存の認証設定に影響しないか | 満たす | `SecurityConfig` は変えていない（最後の変更は 2026-10-14 の `16eb466`）。`httpBasic()` を使わないので、ブラウザが送る `Authorization: Basic` を Spring Security は読まず、`users` のユーザーと混ざらない。コンテナで、正しい資格情報を付けても `/` は 302 で `/login` に移り、フォームログインは今までどおり要った |
| 比較が一定時間で行われるか | 満たす | ユーザー名・パスワードとも、バイト列にして `MessageDigest.isEqual` で比べる（`String.equals()` は使わない）。`&` でつなぎ、ユーザー名が違ってもパスワードまで比べる。設定した値を第 1 引数にしているので、比べる回数は設定した値の長さで決まり、送られてきた値の長さで変わらない。Base64 の読み込みと `:` を探す処理は送られてきた値で時間が変わるが、設定した値の中身とは関係ない |

### 1. 断ったリクエストがリクエストのログに残らない（低）

- 状態：保留
  - 判断メモ（2026-10-19）：今は直さない。違う資格情報は WARN（`Basic auth failed: method, uri`）で残るので、総当たりには気づける。直すには `RequestLoggingFilter` を Basic 認証より前に動かす必要があるが、そうすると Spring Security より前になり、ユーザー ID を MDC に入れられなくなる（CLAUDE.md の「リクエストの追跡」）
  - 見直す条件：Basic 認証で断ったリクエストを、リクエスト ID でたどる必要が出たとき（障害の調査で要った、など）
- 場所：`RequestLoggingFilter` は `DEFAULT_FILTER_ORDER + 1`、`BasicAuthFilter` は `DEFAULT_FILTER_ORDER - 1`
- 何が起きるか：Basic 認証で 401 にしたリクエストは `RequestLoggingFilter` まで届かないので、`request completed` のログに出ない。WARN の行も MDC が空のまま出るので、`[req= user=]` が空になる
- 直し方の案：リクエスト ID だけを付けるフィルターを Basic 認証より前に分ける。または、`BasicAuthFilter` の WARN に、自分でリクエスト ID を作って付ける

### 2. 空白だけの値で有効になる（低）

- 状態：対応済み
  - ✓ 対応済み（2026-10-19、コミット `a88cf3f`。仕様の追記はコミット `7443c3b`）：ユーザー名かパスワードが空白だけなら、`IllegalStateException` で起動しないようにした。空（未設定）のときは今までどおり無効。メッセージに値は入れない。テストは `BasicAuthFilterTest` に 4 件（空白だけのユーザー名、空白だけのパスワード、両方とも空白、タブだけのユーザー名）。本体を直す前に 4 件とも失敗することを確かめた
- 場所：`BasicAuthFilter` のコンストラクタ。`isEmpty()` で「設定あり」を判定していた
- 何が起きるか：Railway で `BASIC_AUTH_PASSWORD` に空白だけを入れると、空白のパスワードで Basic 認証が有効になる。守ったつもりで、実際はほぼ守れていない
- 直し方：空白だけの値を設定の誤りとして起動させない。空（未設定）を無効にする扱いは変えない

### 3. 試せる回数に上限がない（低）

- 状態：保留
  - 判断メモ（2026-10-19）：今は直さない。長いランダムなパスワードを使えば、総当たりで当てられる見込みは小さい。回数の制限は、どのクライアントを数えるか（Railway の手前で IP がどう見えるか）を決めないと作れず、アプリの中に状態（数えた回数）を持つことになる
  - 見直す条件：WARN（`Basic auth failed`）が繰り返し出るようになったとき。または、短いパスワードを使う必要が出たとき
- 何が起きるか：違う資格情報を何度送っても、401 と WARN を返すだけで止めない
- 直し方の案：Railway の手前の仕組み（WAF など）で回数を制限する。アプリで数えるなら、クライアントごとの失敗回数を短い時間だけ覚えて、超えたら 429 を返す

### 4. 実際の登録の順番を自動テストで確かめていない（情報）

- 状態：保留
  - 判断メモ（2026-10-19）：今は直さない。Spring を立てて実際のフィルターの順番を確かめるには DB が要り、今の構成（Testcontainers なし）では自動テストにしにくい。今回は実際のコンテナで手で確かめた（資格情報なしの `/login` が 401）
  - 見直す条件：Testcontainers を入れて、DB を使う結合テストを書けるようになったとき
- 場所：`BasicAuthFilterTest#SpringSecurityのフィルターより前に動く` は、`@Order` の値が `DEFAULT_FILTER_ORDER` より小さいことだけを見る

## 指摘にしなかったもの（2026-10-19）

| 検討したこと | 判断と理由 | 見直す条件 |
|---|---|---|
| `@ConditionalOnProperty` で、環境変数がないときはフィルターを登録しない | 使わない。フィルターを常に登録して中で切り替える。`@ConditionalOnProperty` では、片方だけ設定したときに黙って無効になり、守ったつもりで公開してしまう。今の作りなら起動を止められる | 有効・無効の条件が増えて、コンストラクタでの判定が読みにくくなったとき |
| `SecurityConfig` の `httpBasic()` を使う | 使わない。`users` のユーザーで認証することになり、アプリのログインとは別の関門にならない。フォームログインの設定にも手を入れることになる | Basic 認証をアプリのユーザーで行う仕様になったとき |
| ログイン画面（`/login`）を Basic 認証の対象から外す（Railway のヘルスチェックのため） | 外さない。ログイン画面を見せないことが目的なので、外すと意味が薄れる。Railway の「Healthcheck Path」を外すことで対処する（CLAUDE.md の「本番のコンテナ」） | ヘルスチェックが必要になったとき。Actuator を入れて、ヘルスチェック用の URL を別に作るかを決める |
| Basic 認証が資格情報を暗号化せずに送る | 指摘にしない。Railway の公開 URL は HTTPS なので、通信の途中で読まれない | HTTPS でない場所で公開することになったとき |

## よくできている点

- **設定の誤りで起動を止める**：片方だけ・空白だけの設定を、黙って無効にせず起動エラーにする。守ったつもりで公開する事故を、設定した時点で気づける
- **順番を基準からの相対で決める**：`DEFAULT_FILTER_ORDER - 1` と書き、`RequestLoggingFilter` の `+ 1` と同じ考え方にそろえている。Spring Security の基準が変わっても、前後の関係が崩れない
- **既存の認証に触れない**：`SecurityConfig` を変えず、別のフィルターとして足した。Basic 認証を外す・変えるときに、フォームログインの設定を見直さずに済む
- **守りがテストで固められている**：守りを 7 通り壊して、どれもテストが捕まえた（常に無効、資格情報を確かめない、パスワードを比べない、片方だけを許す、認証の求めを返さない、Spring Security の後に動く、方式名の大文字・小文字を区別する）
